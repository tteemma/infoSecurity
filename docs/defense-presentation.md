# Как показать проект преподавателю

Этот документ — готовый сценарий демонстрации и устной защиты лабораторной
работы № 1.

## 1. Оптимальный порядок демонстрации

Не начинайте с построчного чтения исходников. Сначала покажите поведение
приложения, затем объясните, где и как оно реализовано.

### Шаг 1. Кратко сформулировать цель

Скажите:

> Я реализовал защищённый REST API на Node.js и Express. В нём есть вход с JWT,
> получение данных и создание постов. Данные хранятся в SQLite, пароли
> хэшируются bcrypt, SQL-запросы параметризованы, а пользовательский вывод
> экранируется. Тесты, SAST и SCA автоматически запускаются в GitHub Actions.

### Шаг 2. Показать структуру проекта

```text
src/
├── middleware/       # проверка JWT
├── repositories/     # запросы к SQLite
├── security/         # безопасный вывод данных
├── services/         # аутентификация
├── app.js             # маршруты и сборка приложения
├── config.js          # настройки окружения
├── database.js        # схема SQLite
└── server.js          # запуск HTTP-сервера
```

Скажите:

> Я разделил ответственность. Маршруты работают с HTTP, сервис отвечает за
> аутентификацию, репозитории — за SQLite, middleware — за проверку JWT.

### Шаг 3. Запустить проект

Требуется Node.js 24 или новее.

```bash
npm ci
cp .env.example .env
npm start
```

После запуска API доступен по адресу:

```text
http://localhost:3000
```

### Шаг 4. Показать запрет доступа без токена

```bash
curl -i http://localhost:3000/api/data
```

Ожидаемый результат:

```http
HTTP/1.1 401 Unauthorized
```

Объяснение:

> Все маршруты `/api/*` проходят через единый JWT middleware. Поскольку в
> запросе нет Bearer-токена, middleware возвращает 401, и запрос даже не доходит
> до обработчика данных.

### Шаг 5. Выполнить вход

```bash
curl -s http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"student","password":"ChangeMe123!"}'
```

В ответе будут сведения о пользователе и поле `token`:

```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "user": {
    "id": 1,
    "login": "student"
  }
}
```

Скопируйте токен и сохраните его в переменной:

```bash
TOKEN='полученный-JWT'
```

Скажите:

> Сервер нашёл пользователя параметризованным запросом, проверил пароль через
> bcrypt и выдал подписанный JWT сроком на один час.

### Шаг 6. Получить данные с JWT

```bash
curl -i http://localhost:3000/api/data \
  -H "Authorization: Bearer $TOKEN"
```

Теперь сервер должен вернуть HTTP 200 и массив `posts`.

Объяснение:

> Middleware проверил формат заголовка, подпись JWT, разрешённый алгоритм и срок
> действия. После успешной проверки данные пользователя были записаны в
> `request.user`, и запрос был передан маршруту.

### Шаг 7. Создать обычный пост

```bash
curl -s http://localhost:3000/api/posts \
  -X POST \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title":"Первый пост","content":"Безопасный текст"}'
```

Ожидается HTTP 201 и созданный пост.

Важно отметить:

> Идентификатор автора не принимается от клиента. Он берётся из проверенного
> поля `sub` JWT. Поэтому пользователь не может создать пост от имени другого
> пользователя.

### Шаг 8. Показать XSS-защиту

```bash
curl -s http://localhost:3000/api/posts \
  -X POST \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"title":"<script>alert(1)</script>","content":"<b>текст</b>"}'
```

В ответе специальные символы будут экранированы:

```json
{
  "title": "&lt;script&gt;alert(1)&lt;/script&gt;",
  "content": "&lt;b&gt;текст&lt;/b&gt;"
}
```

Скажите:

> API возвращает JSON, а не HTML. Дополнительно пользовательские строки
> экранируются перед возвратом клиенту. Поэтому при последующем отображении они
> воспринимаются как текст, а не как исполняемый HTML.

### Шаг 9. Показать защиту от SQL Injection

Попробуйте войти с SQLi-строкой вместо логина:

```bash
curl -i http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"student'\'' OR 1=1 --","password":"anything"}'
```

Ожидается HTTP 401.

После этого покажите запрос в `UserRepository`:

```js
.prepare('SELECT id, login, password_hash FROM users WHERE login = ?')
.get(login);
```

Скажите:

> SQL-команда и пользовательское значение передаются драйверу отдельно. Строка
> `OR 1=1` остаётся обычными данными и не может изменить структуру SQL-запроса.

### Шаг 10. Запустить локальные проверки

```bash
npm test
npm run lint
npm audit --audit-level=high
```

Ожидаемые результаты:

```text
tests 11
pass 11
fail 0
```

```text
found 0 vulnerabilities
```

Объясните:

- `npm test` запускает интеграционные тесты;
- `npm run lint` выполняет SAST собственного кода;
- `npm audit` выполняет SCA сторонних зависимостей.

### Шаг 11. Показать GitHub Actions

Откройте:

- репозиторий: <https://github.com/tteemma/infoSecurity>;
- последний успешный pipeline:
  <https://github.com/tteemma/infoSecurity/actions/workflows/ci.yml?query=branch%3Amain+is%3Asuccess>.

Покажите зелёные шаги:

1. установка зависимостей;
2. запуск тестов;
3. `SAST — ESLint Security`;
4. `SCA — npm audit`.

Скажите:

> Workflow запускается при каждом push и pull request. Если тест, SAST или SCA
> завершится с ошибкой, весь pipeline будет красным.

# Готовая речь на 2–3 минуты

> Целью лабораторной было разработать простой защищённый REST API и встроить
> проверки безопасности в CI/CD. Я выбрал JavaScript, Node.js и Express. Для
> хранения данных использовал встроенный SQLite.
>
> В API реализовано три метода: POST `/auth/login` для входа, GET `/api/data`
> для получения постов и POST `/api/posts` для создания поста. Маршруты
> `/api/*` закрыты JWT middleware.
>
> При запуске создаётся демонстрационный пользователь. Пароль перед сохранением
> хэшируется bcrypt с cost factor 12. При входе bcrypt сравнивает переданный
> пароль с хэшем, после чего сервер выдаёт JWT с идентификатором пользователя и
> сроком действия. JWT подписывается алгоритмом HS256, а middleware проверяет
> подпись, срок действия и разрешённый алгоритм.
>
> От SQL-инъекций приложение защищено параметризованными SQLite-запросами.
> Пользовательский ввод никогда не конкатенируется с SQL. От XSS пользовательские
> строки экранируются перед возвратом из API. Дополнительно используются Helmet,
> ограничение тела запроса и rate limit для входа.
>
> Код разделён на базу данных, репозитории, сервис аутентификации, middleware и
> HTTP-маршруты. Это обеспечивает разделение ответственности, DRY и KISS.
>
> Я написал 11 интеграционных тестов. Они проверяют правильный и неправильный
> вход, SQL-инъекцию, XSS, отсутствие токена, изменённый и просроченный JWT,
> валидацию, лимит тела и хранение bcrypt-хэша.
>
> При каждом push и pull request GitHub Actions устанавливает зависимости,
> запускает тесты, SAST через ESLint Security и SCA через npm audit. Финальный
> pipeline прошёл успешно, известных уязвимостей в зависимостях не найдено.

# Частые вопросы преподавателя

## Почему bcrypt лучше SHA-256 для паролей?

SHA-256 специально сделан быстрым. Это удобно для проверки целостности, но
помогает атакующему быстро перебирать пароли. Bcrypt намеренно медленный,
автоматически использует соль и имеет настраиваемый cost factor.

## JWT зашифрован?

Нет. Header и payload только Base64URL-кодированы, поэтому их можно прочитать.
Подпись JWT защищает целостность: если payload изменить, проверка подписи не
пройдёт. Секретные данные в payload помещать нельзя.

## Можно ли отозвать выданный JWT?

В текущей простой реализации — нет, можно только дождаться окончания срока его
действия. Для досрочного отзыва используют denylist или пару короткоживущего
access token и refresh token.

## Почему автор поста не приходит в теле запроса?

Тело запроса полностью контролирует клиент. Если принять `authorId` из body,
пользователь сможет создать пост от имени другого человека. Поэтому автор
берётся из проверенного поля `sub` JWT.

## Почему SQLi и XSS требуют разных способов защиты?

Это разные контексты:

- SQLi предотвращается prepared statements;
- XSS предотвращается безопасным выводом и HTML-экранированием;
- одна защита не заменяет другую.

## Почему не используется ORM?

Для небольшого учебного проекта встроенный SQLite и явные prepared statements
проще. Они непосредственно показывают преподавателю механизм защиты от SQLi.

## Зачем нужен SCA, если собственный код написан безопасно?

Уязвимость может находиться не в собственном коде, а в Express, JWT-библиотеке
или транзитивной зависимости. SCA сравнивает установленные версии с базой
известных уязвимостей.

## Это настоящий CI/CD?

В проекте полностью реализована CI-часть и security pipeline. Автоматического
развёртывания приложения нет, поэтому точнее говорить: «CI/CD pipeline с
автоматическими security-проверками» или «CI-часть процесса CI/CD».

## Зачем нужен фиктивный bcrypt-хэш?

Без него сервер отвечал бы на несуществующий логин почти сразу, а на существующий
логин с неправильным паролем — только после медленного bcrypt. По времени ответа
атакующий мог бы находить существующие логины. Фиктивная bcrypt-проверка делает
оба сценария примерно одинаковыми по времени.

## Почему JWT проверяется только с HS256?

Разрешённый алгоритм задан явно, чтобы заголовок входящего токена не мог
переключить сервер на неожиданный или небезопасный способ проверки.

# Что нельзя говорить неправильно

Не говорите:

> JWT шифрует данные.

Правильно:

> JWT подписывает данные и позволяет проверить их целостность.

Не говорите:

> Bcrypt шифрует пароль.

Правильно:

> Bcrypt вычисляет необратимый адаптивный хэш пароля.

Не говорите:

> HTML escaping защищает от SQL Injection.

Правильно:

> SQLi предотвращают параметризованные запросы, а XSS — безопасный вывод.

Не говорите:

> npm audit проверяет мой JavaScript-код.

Правильно:

> npm audit проверяет сторонние зависимости. Собственный код анализирует ESLint
> Security.

Не говорите:

> У меня применены вообще все принципы ООП.

Правильно:

> Я применил классы, инкапсуляцию, композицию, разделение ответственности и
> внедрение зависимостей. Наследование не добавлял, потому что для этого проекта
> оно не решало реальную проблему и нарушило бы KISS.

# Краткая схема для запоминания

## Вход

```text
логин + пароль
    ↓
валидация
    ↓
параметризованный SELECT
    ↓
bcrypt.compare
    ↓
выдача JWT
```

## Защищённый запрос

```text
Authorization: Bearer JWT
    ↓
JWT middleware
    ↓
проверка подписи, алгоритма и срока
    ↓
request.user
    ↓
маршрут
    ↓
SQLite
    ↓
безопасный JSON
```

## Push в GitHub

```text
push / pull request
    ↓
npm ci
    ↓
11 интеграционных тестов
    ↓
SAST — ESLint Security
    ↓
SCA — npm audit
    ↓
зелёный pipeline
```

Если вы можете своими словами объяснить эти три цепочки, вы понимаете основную
логику проекта и сможете уверенно ответить на большинство вопросов при защите.
